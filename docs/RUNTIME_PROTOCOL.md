# Native simulation protocol v1

The native frontend starts `SimsSimulation GAME WORKSPACE --serve SESSION_DIRECTORY HOUSE --language CODE --profile-id ID`. It sends one JSON object per line over stdin and receives JSON events over stdout. Diagnostics go to stderr. No network server is involved. `--profile-id` is optional and defaults to `player`; native profile IDs are limited to 64 ASCII letters, digits, hyphens or underscores.

The engine replies with `hello`, including the protocol version, architecture, engine ID, content fingerprint and supported commands. It then emits a `frame` containing a scene-file path, increasing revision and current simulation state. The native host calls the core at its configured 60 Hz to produce 30 normal-speed simulation ticks per second. Clients can opt into 30 Hz animation packets. Clients without streaming continue to receive full scenes once per second. The interactive native app enables streaming after `hello`.

Every request has `id` and `op`. A `response` echoes the ID and includes `ok` plus `result` or `error`. For example:

```json
{"id":"1","op":"speed","value":1}
{"id":"2","op":"state"}
{"id":"3","op":"save","slot":"manual"}
```

## Expansion lot transitions

The native server subscribes to the original VM lot-switch event. The Change To Lot primitive continues to populate the engine's cross-lot family state and inventory sim-data effects. The server applies the requested transition after the current VM update finishes. A destination creates a fresh headless VM and loads its original IFF and scripts; destination controllers spawn the travelling Sim or family. The departure time comes from the original inventory effects. A request of -1 returns to the suspended home lot.

The first departure retains a serialized home VM. Moving between expansion lots retains that same home state. Returning resumes the home geometry, objects, clock and execution state with the current family and restores the whole household selection. Transition events use `{"type":"lotChanged","house":21,"away":true}` before a new scene baseline. Scene revisions remain increasing across VMs. The frontend clears old pie menus, dialogs, placement previews and catalog requests, exits editing mode and resets the camera pan when it receives this event. Audio resets at the VM boundary.

Native saves now include an optional `travel` payload containing the suspended home snapshot, home lot identity, travelling Sim GUID, transit mode, active family record/subset and neighborhood inventories. Its optional `neighbors` field serializes the canonical NBRS records, including directional relationships and off-lot person data represented by the engine. This field is saved at home as well as away. Restore keeps the provider's existing chunk identity. The NBRS writer counts active records and orders them by neighbor ID, so unoccupied slots cannot corrupt its header. The separate family record covers saves taken before a destination controller activates the family. Away saves can load from the corresponding home session or another destination in the same trip. Engine and pack fingerprint checks still apply. Legacy home saves without this field remain readable only from their original home lot. Same-lot loads retain the chosen editing view. The SIMI writer preserves its source globals and uses matching version/header lengths for both base and expansion records. Native Sim selection follows original destination control commands.

Headless verification is available with `dotnet native/SimsSimulation/bin/Release/net9.0/SimsSimulation.dll "$PWD/runtime/game" "$PWD" 5 0 --check-travel`. It invokes the original travel primitive, runs destination scripts, checks traveller activation, serializes and restores away funds/inventories, then returns to the suspended home. The native frontend maps the original neighborhood-dialog types to modes 2, 3, 4, 5, and 7, renders their original neighborhood and lot resources, and returns the selected lot through the same blocked dialog. All configured maps (modes 1, 2, 3, 4, 5, and 7) now export and render from the installed resources at 800×600 and 1920×1080 after merging missing expansion route chunks. Escape submits the original `-1` return-home choice. Swift mapping/response tests and the 66-check travel scenario pass; an end-to-end hit-region-to-simulation test and complete expansion gameplay coverage remain outstanding.

The native host reads the Windows language identifier from the installed `Sims.exe` version resource and maps it to the matching Sims `STRLangCode` before loading IFF content. It passes the code to the simulator as `--language`; the `hello` event reports `languageCode` so the frontend can verify the active setting. If the executable is missing, its resource metadata is malformed, or the language is unsupported, both sides use English (US), matching FreeSO's original `STR.DefaultLangCode` fallback. The family/CAS overlay reads localized strings from installed `GameData/UIText.iff` tables 129, 130, and 164 using the detected code. Career and Interests panels read skill and status labels from STR# tables 160, 166, 158, and 154. Other Swift-authored screens and dialogs still contain English text.

`createHousehold` accepts one to eight human Sims and requires at least one adult. Appearance codes contain `m` or `f`, then `a` or `c`, then a three-letter body type (for example `mafit`); skin is `lgt`, `med` or `drk`. Optional `headChoice` and `bodyChoice` IDs must match resources returned by `appearanceCatalog` for the same gender, age and skin. The server resolves both from the installed BCF and avatar texture providers and writes the selected original body strings into each new character resource. `appearancePreview` uses those same validated IDs and emits a schema-versioned JSON manifest plus BMP/TGA files under the active session's `cas-preview` directory. Files are temporary session output; the installed game resources remain read-only. Personality values are 0–1000 in increments of 100 and must distribute exactly 25 points across the five original traits. The current generated default household budget is $20,000 before lot purchase. The native app now opens an original-background family and Create-a-Sim flow when the player chooses an affordable vacant residential lot. It supports family membership, names, biography, gender, age, skin tone, head/outfit selection, personality, and the personality-derived zodiac, with original Add/Edit/Delete, gender, age, skin, Done and Cancel button sheets. The preview is rendered with the original selected head and outfit meshes. Cancel from the family screen returns to the retained neighborhood without autosaving the empty lot. Exact original control placement and a family/import picker remain incomplete.

The `neighborhood` manifest uses schema version 2. Each lot entry includes `occupied`, `residential` and `availableForCreation`; creation is available only on an affordable, vacant residential lot in the base neighborhood. Expansion travel destinations keep their original dialog response path.

Architecture commands use the original `VMArchitectureCommandType` names: `WALL_LINE`, `WALL_DELETE`, `WALL_RECT`, `PATTERN_DOT`, `PATTERN_FILL`, `FLOOR_RECT`, `FLOOR_FILL`, `TERRAIN_RAISE`, `TERRAIN_FLATTEN`, `GRASS_DOT`. The meanings of `x2`, `y2` and `style` depend on the command. For `FLOOR_RECT`, zero width and height address one tile. Coordinates use the simulation's lot orientation. Read the floor catalog and buildable flags before issuing edits.

Queued replies acknowledge submission. Architecture transactions and interactions execute on later VM ticks; their effects must be verified in subsequent state events. This interface is intended to support the original frontend and future authoring tools. The native pie menu uses this interface; the original build/buy interface remains incomplete.

Object editing requires a paused simulation, an active household and no blocking dialog. Object coordinates use sixteenths of a tile: tile `(10, 12)` has center `(168, 200)`. `level` starts at one. Directions are `1` north, `4` east, `16` south and `64` west. Coordinates must be inside the buildable area. The engine applies object-specific placement rules, purchase transactions, refunds for failed placements and resale prices. Avatars and objects that the engine marks immovable or unsellable are rejected. Unknown catalog GUIDs and purchases exceeding family funds are rejected before submission.

Each item includes `guid`, original catalog `name` and `description` from CTSS, `price`, `category` and optional `icon`. Icons use the same immutable BMP references as gameplay portraits, relative to the session scene directory. Paired catalog icons have two columns. Catalog reads do not instantiate objects or charge the family. A request past the category's end returns an empty page.

Save slots contain ASCII letters, digits, hyphens or underscores and are limited to 64 characters. Save files live in `DATA_ROOT/runtime/native-profiles/PROFILE_ID/Saves`; the app's `DATA_ROOT` is `~/Library/Application Support/Sims Native`, while developer and command-line runs default it to the workspace. Their envelope includes the engine ID, house, content pack fingerprint and compressed FreeSO snapshot. Loads reject another engine, another lot or a different pack stack. Pack asset hashes are included in the fingerprint, so changed content requires an explicit migration rather than silently loading incompatible IDs.

The frontend clones game files into a session content mount and applies ordered packs there. Native Sims receive stable player identifiers based on their neighborhood IDs, with separate identities for otherwise colliding NPCs. This makes architecture costs and interaction callers resolve to avatars instead of objects sharing the legacy zero ID.

Scenes include ground-floor sprites and original avatar meshes, a `wallsUp` flag, a `wallSprites` count and optional `terrainVertices`. Optional `lotWidth` and `lotHeight` identify the tile grid; when supplied together, dimensions must be `1..128` and terrain must contain six vertices per tile in row-major order. The native ground picker tests both projected triangles per tile, including sloped terrain. Older scenes without grid dimensions still render but cannot supply ground placement coordinates. Terrain vertices form an unindexed triangle list with projected `x`, `y` and byte-valued `r`, `g`, `b` colors. Swift bounds-checks geometry and renders it with a Metal vertex buffer. Original wall patterns are composited with their original style masks, including object-supplied door/window shapes in walls-up mode. Wall junctions, exact cutaway parity, sloped floor texture deformation, localized light maps and shadows remain incomplete.

Each optional `meshes` entry contains `texture`, `objectID`, an interleaving `depth`, and an unindexed triangle list. Vertices contain projected `x`/`y`, normalized GPU depth `z`, texture coordinates `u`/`v`, and `nx`/`ny`/`nz` normals. Original bone bindings and animation states produce the posed meshes on the simulation side. Texture entries carry `encoding` (`rgba`, `bmp`, `tga` or `depth8`), dimensions and a scene-relative immutable file path. Swift validates triangle counts, bounds, finite values, texture indices and decoded dimensions before creating GPU buffers. Live animation uses incremental pose packets; sub-tick and slot transition interpolation remain incomplete. Shared placement now resolves original SLOT containment, nested objects, animated hand/head/pelvis bones, Sim scaling and terrain heights.

Object sprites with original SPR2 depth data include `depthTexture`, `depthNear` and `depthFar`. These fields are optional for older scenes, but must appear together. The depth texture uses `depth8`: exactly one byte per pixel, with the same dimensions as its color texture. It cannot be used as a color texture. Intervals must satisfy `0 <= depthNear <= depthFar <= 1`.

Metal reads depth texels without filtering and maps values 0 through 254 onto the supplied interval. Value 255 discards the fragment, as does color alpha below 0.25. Sprite flipping applies to both textures. Depth sprites and avatar triangles share the same depth attachment with writes enabled and a less-or-equal comparison. The simulation projects both through `NativeDepth`, including terrain elevation. Walls, floors and sprites without depth maps retain draw ordering.

The sentinel and normalization match the recovered Legacy fragment shader at `analysis/legacy-shaders/008bf478.spvasm`. The sprite interval derives from FreeSO's DGRP offsets and depth span, adapted to our fixed isometric projection. Exact Legacy camera calibration and all wall/object intersections remain unverified. Run `python3 tools/check_native_depth.py` for twelve actual Metal renders covering both draw orders, flipped UVs, transparency, the sentinel, two resolutions, scene reloading, streamed mesh replacement and newly appended textures. Results are written to `logs/native-depth-result.json`; full-lot integration also checks original depth exports.

Resume and pause controls remained responsive. This is a manual live check, separate from the automated offscreen GPU checks.

The CLI `--reload-scene PATH` option also replays the live import path before an offscreen render, though that replay alone did not reproduce the window failure.

Loading a lot (entering it, reloading the household, or coming home) restores from that chunk when it belongs to the family that lives there now, and otherwise rebuilds the lot from its original object map. Objects of packs that are no longer installed are removed and refunded, as for slot loads. Evicting the family drops the chunk. The lot thumbnails in the house file are not regenerated. ## Gameplay state and resources

Each Sim includes `household`, `portrait`, `mood`, eight named `motives`, and `actions`. UI image references carry `file`, `columns`, and `rows`; their immutable, SHA-256-named BMP files live alongside scene textures. Portraits use original character chunk 2002. Object icons use the original catalog icon chunk, with two columns for the standard paired TS1 icon. The client bounds-checks image size and dimensions and confines references to the current scene resource directory.

`neighborID` identifies the original neighborhood record independently of the current lot object ID or display name. `personality` carries the raw Neat, Outgoing, Active, Playful and Nice person-data values; one visible point is 100 units. `personType` and `zodiac` also retain their raw signed values. The frontend derives an unset zodiac using the original profiles for display, without changing simulation data. Panel selection is local frontend state and persists while selecting another resident. Pet personality labels are not implemented, so their personality button remains disabled.

Each Sim's optional `relationships` array reads the original neighborhood matrix without spawning target avatars. Entries carry `neighborID`, `guid`, original `name`, raw signed-short `values`, `household`, `reverseDaily`, `famous` and an optional original five-expression BMP 2003 portrait reference. Daily relationship is index 0 and lifetime relationship is index 2; all other values remain intact for scripts and expansion behavior. The native client accepts this data independently of lot object IDs. The original relationship panel displays daily/lifetime numbers and bars, portrait expressions, mutual-friendship, crush and love icons, four filters and paging whose capacity follows the available logical width. At 800/1024/1200 logical pixels it fits 5/10/14 cards; interests fit 2/3/5 columns of three rows. The same layout controls rendering, arrows, paging and hit testing, and resizing retains the previously visible item within the new page. `mutualFriend` is true when both daily scores reach `friendship_threshold`, loaded from the simulator constants (FCNS 2 in `Global.iff`; 50 in the shipped game, built-in default 25); crush and love read indices 1 and 3.

`--check-relationships` runs the original relationship primitive in both directions against off-lot targets, checks native export, then saves and restores neighborhood social/person data through the server. It also checks empty neighbor slots and rejects a truncated record count. The current fixture passes 276 checks against 30 off-lot Sims, without changing original game data or opening a live game window.

`skills` carries raw Cooking, Mechanical, Charisma, Body, Logic and Creativity values. `career` carries raw job `type`, `level`, `performance`, `age` and `atWorkSchool`, together with `track`, `title`, `salary`, `startHour`, `endHour`, `currentLevelRequirements` and `nextLevelRequirements` from the mounted work.iff CARR records. Missing or out-of-range levels produce null level metadata. The ten requirements retain their original order: friends, Cooking, Mechanical, Charisma, Body, Logic, Creativity and three additional fields. The original `0x004ea908` getter selects level + 1 for promotion markers; these disappear once the corresponding raw skill meets that value. The export does not predict whether a promotion will occur.

`interests` contains 19 raw signed person-data values in the original icon order, including the four child aliases. The frontend selects the original eight child topics for ages 1..17 and fifteen adult topics otherwise. Transport preserves raw values; drawing uses ten 100-unit points and original bitmap bars. See `docs/ORIGINAL_UI.md` for the field mapping and current presentation limits.

Children under 18 use the school CARR record's first level for displayed title, pay and hours while retaining their raw grade in `level`. `school` makes that display choice explicit. `performanceLabel` comes from work.iff STR# 4096 for five work ratings, or STR# 4097 for sixteen school grades. `familyFriends` exposes the same current FAMI counter that the simulation reads; relationship-driven freshness of that counter remains unverified. The Career panel retains its mode when switching among supported residents and falls back to Needs for unsupported Sims.

Actions include `token`, `name`, `callee`, `active`, `visible`, `cancellable`, `cancelRequested`, and optional `icon`. Tokens identify actual queue instances within a server session rather than relying on the engine's wrapping 16-bit UID. Loading a save creates new queue instances and fresh tokens; a click from the earlier state cannot cancel a newly restored action. Hidden idle and parent-exit entries stay in state for diagnostics but are filtered from the native row. Must-run and parent-exit actions are not offered for cancellation. A blocking dialog also prevents cancellation.

Cancellation calls `VMNetInteractionCancelCmd.Execute` synchronously on the simulation loop after validation. ## Incremental animation

A streaming `animation` event contains `frame` with `schemaVersion: 1`, `baseRevision`, a monotonically increasing `sequence`, `updates`, `textureStart`, appended `textures`, dynamic `sprites`, and packed `meshes`. It contains all currently visible ground-floor object sprites and Sim meshes. The client replaces the previous dynamic lists; disappearance therefore removes hidden/deleted/moved-upstairs visuals. The original ground, floor and wall geometry stays resident. Static snapshots refresh every five seconds while running, and after architecture commands, wall-mode/story changes, stepping, loading or explicit scene requests. State updates remain once per second, with immediate events for dialogs. Pausing or a blocking game dialog stops animation packets.

Each packed mesh carries `texture`, `objectID`, `depth`, and a base64 `vertices` buffer. Each vertex is eight little-endian 32-bit floats in `x, y, z, u, v, nx, ny, nz` order, with three vertices per triangle. Coordinates use the current baseline's origin and bounds. `textureStart` must match the client's current texture count; new entries append to that table. Texture files are immutable content-hashed resources in the baseline scene directory. Source sprite decoding, avatar texture bytes and texture indices are cached across packets. The frontend uploads appended textures and new mesh buffers, keeps the terrain buffer, and updates picking to use the same animated geometry as Metal.

The frontend rejects a different baseline revision, repeated/out-of-order sequence, texture-table mismatch, invalid triangle byte count, nonfinite/out-of-bounds values and memory-limit violations before replacing the visible scene. A packet has a 16 MiB transport limit and at most 32 MB of unpacked vertex bytes. A replay file has a 128 MiB limit and at most 300 packets. Whole-scene JSON files have revision-specific names, preventing a later export from replacing a pending import. `sceneAck` cleanup retains two snapshot files; it never deletes referenced immutable texture files. Speed changes, dialog responses and explicit stepping reset the wall-clock schedule so command processing does not become extra simulation time after resume.

`view { "editing": BOOLEAN }` controls the buy/build visibility exemption. State exposes `editingView`. Buy/build mode changes submit true and live mode submits false. This affects visual hiding only: it does not grant editing permission, change simulation speed or alter object state. During editing, HideForCutaway objects remain visible; the ordinary Hidden state still applies. The headless harness explicitly selects editing view for editing commands, matching the native frontend.

Wall geometry now exposes cuts and up/down junction flags in a single canonical `WallComponent.GenerateGeometry` pass. Native snapshots select junction frames through the engine lookup and original walls.iff SPR 4097 artwork, with engine procedural junction depth data. Optional sprite `junction` metadata carries x, y, level, flags, frame and down; Swift rejects invalid bounds, frame indices, dynamic object ownership and absent depth textures. Junctions retain outside room lighting and stay static across animation updates. Headless checks verify full/low junction projection and depth presence. Camera rotation and exact depth parity with the original executable remain unfinished.

Native wall bodies, fences, diagonal walls and cutaway overlays now export procedural depth textures through the same cache used for junctions. Medium orientations select engine `WallZBufferConfig` entries 4..7; each texture samples the original depth grid at its own dimensions, preserving zero-to-254 depth values while reserving 255 for transparent depth pixels. The sprite interval uses the shared native projection and the engine wall origin at terrain coordinate (x,y) plus story elevation. Optional `architectureDepth` metadata carries x, y, level and configuration. It requires static ownership, valid lot coordinates, a matching story, configuration 4..7 and a depth texture; any wall picking metadata must identify the same tile. Static architecture depth survives animation replacement.

The cutaway headless check compares exported depth bytes against the orientation formulas. Thirty-two offscreen lot renders include controls with junctions removed and wall depth disabled, confirming visible changes within the lot and identical original UI. Twenty-four isolated Metal depth cases verify near/far coverage, draw-order independence, flipped sampling, transparency, the sentinel and static wall retention through animation at two resolutions. This does not establish exact depth mapping parity with the original executable, camera rotation or wall deformation on sloped terrain.

Avatar mesh export includes bound script/animation appearances. No separate frontend command is needed: simulation changes to `BoundAppearances` are consumed by the next snapshot or animation frame. Shared VM bind/unbind methods normalize bare names and `.apr` names for suit primitives and animation dress/undress events, including case aliases. Native export also resolves names from older saves without duplicate visual bindings. Changes refresh the cached body/head/hand/accessory combination; unchanged sets retain it. The current pose, hand gestures, carry pose, head seek, skin tone, story, lighting and scaling apply to all accessory meshes through the existing shared avatar geometry path. Missing appearance dependencies retain the valid avatar parts and are exported as `avatar-appearance:ID:RESOURCE:ERROR` entries in `missingResources`; animation frames now also include `missingResources`. Run `python3 tools/check_native_appearances.py` for original and isolated custom CMX attachment lifecycle plus streamed/full-scene pixel comparisons. Live testing remains deferred.

## Neighborhood persistence and behavior audit

Native travel/save snapshots optionally include `neighborhoodData` (all 16 signed values) and `typeAttributes` (GUID-keyed signed arrays), alongside the complete NBRS records. Older snapshots omit these fields and retain their previous behavior. Type-attribute restoration keeps the provider's canonical TATT chunk instance, validates duplicate GUIDs and bounds record/value counts before replacement, and clones arrays on save and restore. Shared script scopes 36/37 read and write these restored tables.

Modern neighbor records preserve all 256 values. Legacy version-4 records retain their original 80-value encoding and the engine's 88-value compatibility array. Scope 32 accepts indices 0–255, returns zero for an existing neighbor without serialized person data or beyond a legacy array, and rejects an absent neighbor. Scope 34 reads indices 1–15 from canonical NGBH data. Both scopes are read-only in the original executable. The same original dispatch establishes read-only setters for slots, room information, neighbor lookup and job data.

`--audit-behaviors` produces a static inventory of every loaded object resource plus global and referenced semiglobal routines. It reports primitive registration, reference sites, unresolved routine references and resource load errors. The initial inventory contains 5,270 object definitions, 1,234 resources, 28,570 routines and 399,256 instructions. It found 73 references to unregistered primitive opcodes 10, 33 and 34, plus 221 unresolved routine references, mostly deliberate-looking 32767/65535 values. These references require behavioral review; registration and reference resolution do not establish gameplay completeness.


## Household move-in, plugins and save backups

These commands are implemented but have not been built or exercised by the final gate yet.

- `moveInFamily` `{family}` moves an unhoused family from Neighborhood.iff onto the paused, vacant residential lot. The engine charges the lot's SIMI purchase value and rejects occupied, non-residential or unaffordable lots. The neighborhood export now includes `families` (unhoused, non-townie families with `id`, `name`, `budget`, `netWorth`, `friends`, `members`) and per-lot `price`, `community`, `houseName`, `houseDescription`, `street`, `familyName`, `familyNetWorth` and `familyFriends`. `--check-family-move-in` exercises the rule on an isolated profile.
- Native saves now use envelope schema 2. It adds `packs` (`id`, `version`) and `plugins` (namespaced plugin state). Schema 1 saves still load. A save loads when its pack fingerprint matches. It also loads when every saved pack is still enabled and each changed version is listed in the pack's `saveMigration.from`. Newly enabled packs are allowed. Before a migrated load, and before every overwrite, the slot is copied to `Saves/backups/<slot>-<UTC timestamp>.json`. The newest five copies are kept. `saveBackups` `{slot}` lists them and `restoreBackup` `{slot, backup}` restores one; the current slot is backed up first. Event `saveMigrated` reports upgraded packs and the backup name. A save that records a pack which is no longer enabled fails with `missingPacks` (`id@version` strings) in the response; `load` `{slot, removePacks: true}` then removes that content (see "Uninstalling a pack" in `docs/PACKS.md`), and `saveMigrated` adds `removed`, `removedObjects` (`guid`, `objectId`, `name`, `refund`), `refund` and `resetObjects`.
- `plugins` returns plugin load states and declared panels. `pluginPanels` returns bound panel values. `pluginAction` `{packId, panelId, action}` forwards a panel button to its plugin. Events: `plugin` (`loaded`, `untrusted`, `rejected`, `failed`) and `pluginPanels`. `hello` includes `plugins`, `pluginPanels` and `saveSchemaVersion`.
